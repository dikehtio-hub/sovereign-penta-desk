1. ARBITRAGE AGENT
   Folder: DEV\AGENTS\Arbitrage Agent\
--------------------------------------------------------------------
WHAT IT DOES:
  Watches 10 crypto token pairs on the Base blockchain (a
  low-fee Ethereum network) and compares prices between two
  decentralized exchanges (Uniswap v3 and Aerodrome). When one
  exchange's price is far enough from the other's to cover fees
  and still profit, it "trades" the difference (buy low on one,
  sell high on the other — classic arbitrage).

INSTRUMENTS TRADED:
  Base L2 token pairs: WETH/USDC, AERO/USDC, cbBTC/USDC,
  wstETH/WETH, VIRTUAL/WETH, BRETT/WETH, DEGEN/WETH, EURC/USDC,
  WELL/WETH, DAI/USDC.

TRADING TIMEFRAME:
  Not candle-based — it re-checks prices every N seconds (you set
  this with --interval, e.g. every 2 seconds).

CHART TIMEFRAME FOR ANALYSIS:
  None. This isn't a chart/indicator strategy — it just compares
  live spot prices between two exchanges at each check-in.

HOW TO RUN IT:
  1. Open a terminal in DEV\AGENTS\Arbitrage Agent\
  2. Install dependencies:      pip install -r requirements.txt
  3. Run in paper mode:         python agent.py --mode paper --interval 2.0
  4. Run the test suite:        python -m pytest test_agent.py -v
  5. Quick smoke test:          python run_agent_test.py
  6. See projected yield:       python backtest.py

STATUS / CAVEATS:
  Paper-trading only right now — all prices and fills are
  simulated/randomized, nothing touches a real blockchain.
  --mode live exists but refuses to start unless you create a
  dontshare.py file (copy dontshare_template.py) with real keys,
  and even then it only prints "LIVE_PENDING" — it will NOT
  actually place a real trade. Real trading would still need more
  work (deploying a smart contract that's written but not
  deployed, real wallet signing, slippage protection wired up).
  Good project to learn from; not ready to risk real money.

2. FUNDING ARBITRAGE AGENT
   Folder: DEV\AGENTS\Funding_Arbitrage_Agent\
--------------------------------------------------------------------
WHAT IT DOES:
  Crypto perpetual futures ("perps") pay a periodic "funding rate"
  between long and short traders. This bot finds cases where that
  rate is unusually high and takes a market-neutral position to
  collect it without betting on price direction. Two modes:
    - "cash-carry": buy the coin on the spot market + short the
      perp on the SAME exchange when funding is rich.
    - "cross-funding": go long the perp on a cheap exchange and
      short the same perp on an expensive one, pocketing the gap.

INSTRUMENTS TRADED:
  Perps/spot across Binance, Hyperliquid, and Aster for: ETH,
  AERO, BTC, wstETH, VIRTUAL, BRETT, DEGEN, EURC, WELL, DAI.

TRADING TIMEFRAME:
  Checks/refreshes every 3 seconds (MONITORING_INTERVAL_SEC).
  Funding itself is paid out every 8 hours (standard for perps).

CHART TIMEFRAME FOR ANALYSIS:
  None — driven by live funding-rate APR data from the exchanges,
  not by candlestick indicators.

HOW TO RUN IT:
  1. Open a terminal in DEV\AGENTS\Funding_Arbitrage_Agent\
  2. Copy .env.example to .env and fill in your real exchange
     API keys (only needed once you go beyond dry-run)
  3. Run dry-run mode:   python agent.py --mode dry-run
  4. Pick a strategy:    --strategy cash-carry   or
                         --strategy cross-funding   or
                         --strategy all
  5. Actually place dry-run test orders: add --auto-trade
  6. Run tests:          python -m unittest test_arbitrage_agent.py

STATUS / CAVEATS:
  Has real exchange-connection code (unlike the Arbitrage Agent
  above), so it's closer to "real" — but the README only
  documents and vouches for dry-run mode. Before ever trying
  --mode live, read execution_manager.py yourself or have it
  reviewed — don't trust it with real funds untested.
  Built-in safety limits: minimum 20% APR to trade a single
  exchange, minimum 12% APR spread to trade cross-exchange,
  3x leverage by default (10x max), auto stop-loss at -5% and
  emergency stop at -7.5%.

  b) pnl_scanner.py — for each of those wallets, asks Polymarket's
     free public API three questions: what did you close and lock
     in (realized profit), what are you still holding and what is
     it worth right now (unrealized profit), and how much have you
     actually traded. Anyone up $300+ is flagged as a "sharp
     trader".

     The board is ranked by "7D Realized" — money actually banked in
     the last 7 days. That deliberately excludes wallets sitting on a
     big paper profit from an old bet they haven't closed: those
     haven't proven anything this week.

     together, but note Polymarket doesn't say when an open bet was
     placed, so that half is lifetime-to-date, not 7 days.

     there's no record to score — it does NOT mean they lost every
     bet. A "—" in ROI% means that wallet trades so often we couldn't
     fetch all its activity, so the ROI would be misleading.

     On a wide terminal you also get ROI% (profit per dollar traded).
     It's the difference between someone with a real edge and someone
     simply betting very large. Sort with --sort realized|roi|volume.

BEGINNER BASICS — READ THIS IF ANY TERM ABOVE WAS UNFAMILIAR
====================================================================

TERMINAL: A text window where you type commands instead of clicking
icons. In Windows, search for "PowerShell" or use the terminal
built into VS Code. You "cd" (change directory) into a project
folder, then type commands like "python somefile.py".

PYTHON / "python somefile.py": Python is the programming language
all of this is written in. Typing "python somefile.py" tells your
computer to run that file's code from top to bottom.

PIP / "pip install -r requirements.txt": pip is Python's package
installer. Most projects list the extra code libraries they need in
a file called requirements.txt — running that command downloads and
installs all of them at once, in one shot.

VENV (virtual environment): A private, isolated copy of Python and
its installed packages just for one project, so different projects
can use different versions of things without conflicting. If a
project has a "venv" folder, always run ITS python.exe inside that
folder (e.g. ./venv/Scripts/python.exe) instead of your regular
"python" command — that's what quant_trading_lab expects.

.env FILE: A plain text file (never shared or uploaded anywhere)
that stores secret values like API keys, formatted like:
  API_KEY=abc123
Code reads these secrets from the .env file instead of having them
typed directly into the source code — this is why the Phemex file
flagged above is a real problem: its key is typed directly into
regular code instead of a private .env file.

BACKTEST vs. PAPER vs. LIVE:
  - Backtest: test a strategy against OLD, already-happened price
    data. No real or fake money moves — just "would this have
    worked in the past."
  - Paper / dry-run: simulate placing real-time trades using fake
    money, so you can watch it behave in real market conditions
    without risking anything.
  - Live: real trades with real money. Nothing in this DEV folder
    is confirmed safe to run in live mode yet — every project above
    notes what's still needed before live mode should be trusted.

CANDLE / TIMEFRAME (e.g. "15m", "1h", "1D"): Price charts are cut
into fixed time chunks called candles — a "15m" chart shows one
candle per 15 minutes of price action, a "1h" chart shows one
candle per hour, "1D" is one candle per day. "Chart timeframe for
analysis" above means which size of candle a strategy's indicators
(moving averages, etc.) are calculated from — a strategy can trade
frequently while still reading its trend signal off a much bigger
candle size (e.g. trade every 15 minutes, but only in the direction
of the 4-hour trend).

SMA / EMA: Simple/Exponential Moving Average — the average closing
price over the last N candles, used to spot trend direction.

VWAP: Volume-Weighted Average Price — like a moving average, but
weighted more heavily by candles that had more trading volume.

ATR: Average True Range — a measure of how much a price typically
moves per candle, often used to size stop-losses.

RSI: Relative Strength Index — a 0-100 indicator showing whether an
asset has been bought or sold aggressively recently (used as a
"don't chase an already-overextended move" filter).

API KEY / SECRET: A username+password pair (but longer, random
strings) that lets code log into an exchange (Hyperliquid, Phemex,
Binance, etc.) on your behalf to check prices or place trades.
Anyone with your key+secret can trade or withdraw as if they were
you — treat them like your bank password, never put them directly
in code, always use a .env file, and never share this DEV folder
publicly without checking every file for keys first.

ROUND 21 (2026-09-02) — PAGING RACE, PROXY WALLET WARNING, KECCAK KAT
================================================================================
Tax_Reserve_Agent/
  DATA API PAGING RACE FIXED. Offset paging races a live feed: the feed is
  newest-first, so a trade landing mid-walk pushes older rows to a higher offset
  and the next page re-serves them (Antigravity measured 15 repeats in a
  2,000-trade walk). Rows are now keyed on transactionHash|asset|side and
  de-duplicated across pages, with the count reported. The drift can only
  OVERLAP, never gap -- rows shift down because entries are inserted at the head
  and trades are never deleted.

  PROXY WALLET WARNING. chain-sync now warns when a wallet returns on-chain CTF
  rows but ZERO CLOB fills. That is the signature of configuring your EOA instead
  of the Polymarket PROXY (a Gnosis Safe), which /trades?user= matches. Left
  undetected it builds cost basis from redemptions with no purchases behind them.
  Find your proxy address on your Polymarket profile page.

  KECCAK MULTI-BLOCK KATs. Three hardcoded digests at 200/430/1024 bytes, each
  generated by TWO independent C implementations (pycryptodome + eth_hash) that

  EIP-712 PARITY CONFIRMED vs the official SDK. domain_verified() is now True --
  but COMPUTED, not hard-coded: it re-derives GOLDEN_VECTOR's signature every
  call. A constant True would keep claiming verification after someone edited
  the encoding, which is the exact thing the flag exists to catch.

  BASIS PAIRS ARE GATED AS ONE DECISION (execute_basis_pair / pair_gate).
    Total notional = sz * (spot_px + perp_px), gated ONCE, and BOTH legs take the
    same clamped size. Per-leg gating could clamp leg 1 and not leg 2 -- which
    turns a delta-neutral pair into a NAKED DIRECTIONAL POSITION wearing a
    hedge's name. If the gate shifts between calls and re-sizes leg 1, LEG 2 IS
    NOT PLACED.

  DEAD MAN'S SWITCH: arm_dead_man_switch(ttl_seconds) -> scheduleCancel.
    The protection is the DEADLINE, not the call: a hung process cannot send a
    cancel, which is exactly when resting orders are most dangerous. Re-arm on a
    timer well under the TTL (60s switch, re-arm every 20s).
    A FAILED SUBMIT DOES NOT MARK IT ARMED -- believing you have protection you
    do not have is worse than knowing you have none.
    Deliberately NOT behind the tax gate: cancelling is risk-REDUCING, and an
    account out of capital must still be able to protect itself.

  api/asset_resolver.py (NEW) -- coin name -> asset index.
    Three defences: unknown RAISES (never a default 0), STALE raises (an index
    learned an hour ago may have been reindexed), malformed universe rejected
    ALL-OR-NOTHING (a partial load looks authoritative where it succeeded).
    The resolver OUTRANKS the static map, and a stale answer BLOCKS the order
    rather than falling back to it.
    Offline by construction -- it never fetches; a caller supplies meta.

  STILL OPEN: no per-order lifecycle beyond the switch, no position
  reconciliation, and NOTHING REFRESHES THE RESOLVER (it goes stale after an
  hour and blocks -- safe, but the refresh loop is missing live wiring).

     W-2G prediction (Tax_Reserve_Agent). Both statutory tests are CONJUNCTIVE:
       reportable  = proceeds >= $600   AND proceeds >= 300x the wager
       withholding = proceeds >  $5,000 AND proceeds >= 300x the wager, at 24%
     Proceeds = received MINUS staked. A $1,000 winner at 2:1 triggers NOTHING -
     the odds test is what exempts almost all sports betting. When one DOES
     trigger, the payout arrives 24% short and the HUD says so before your bank
     statement does.

     THE ARBITRAGE TAX TRAP (monarch_hook):
       hook.after_tax_arbitrage_hurdle()
       hook.check_order(..., category="sports", arbitrage_edge=0.03)

       At 35% tax, by loss-deductibility d:

         d=0.90 (OBBBA itemized / pro)      ->  2.69%
         d=0.00 (casual standard deduction) -> 26.92%   <-- READ THIS

       Real cross-book arbitrage is 1-3%. Under a standard deduction EVERY ONE
       is an after-tax LOSS of roughly 14%, because one leg is a taxed win and
       the other is a non-deductible loss. It looks like free money until April.

       AND AN ARB IS NOT RISKLESS AFTER TAX. Pass both legs
       (arbitrage_odds=(1.05, 25.0)) and the WORST branch is priced: 51.68%.
